leveldb 日志格式
==================

> 本文为 [doc/log_format.md](../log_format.md) 的中文译本。

日志文件内容是一串 32KB 的块。唯一例外是文件尾部可能包含一个不完整的块。

每个块由一串记录组成：

    block := record* trailer?
    record :=
      checksum: uint32     // type 与 data[] 的 crc32c；小端序
      length: uint16       // 小端序
      type: uint8          // FULL、FIRST、MIDDLE、LAST 之一
      data: uint8[length]

记录绝不会在块的最后六个字节内开始（因为放不下）。此处剩余的任意字节构成 trailer，必须全部为零字节，并且读者必须跳过它们。

补充：若当前块恰好剩余七个字节，并且要添加一条新的非零长度记录，写者必须发出一条 FIRST 记录（用户数据长度为 0）填满块尾的七个字节，然后将全部用户数据写到后续块中。

将来可能增加更多类型。有些读者可能会跳过其不认识的记录类型，另一些则可能报告部分数据被跳过。

    FULL == 1
    FIRST == 2
    MIDDLE == 3
    LAST == 4

FULL 记录包含整条用户记录的内容。

FIRST、MIDDLE、LAST 用于被拆成多个片段的用户记录（通常因为块边界）。FIRST 是用户记录第一个片段的类型，LAST 是最后一个片段的类型，MIDDLE 是所有中间片段的类型。

示例：考虑如下用户记录序列：

    A: length 1000
    B: length 97270
    C: length 8000

**A** 将作为 FULL 记录存储在第一个块中。

**B** 将拆成三个片段：第一个片段占用第一个块的剩余部分，第二个片段占用整个第二个块，第三个片段占用第三个块的前缀。这样第三个块会留下六个空闲字节，作为 trailer 保持为空。

**C** 将作为 FULL 记录存储在第四个块中。

----

## 相对 recordio 格式的若干优点：

1. 我们不需要任何用于重新同步的启发式方法——只需走到下一个块边界并扫描。若发生损坏，跳到下一块。附带好处是：当一个日志文件的部分内容作为记录嵌入另一个日志文件时，我们不会混淆。

2. 在近似边界处拆分（例如用于 mapreduce）很简单：找到下一个块边界，并跳过记录直到遇到 FULL 或 FIRST 记录。

3. 对大记录不需要额外缓冲。

## 相对 recordio 格式的若干缺点：

1. 不打包极小记录。可通过增加新的记录类型修复，因此这是当前实现的不足，不一定是格式本身的问题。

2. 无压缩。同样可通过增加新的记录类型修复。
